# Cart and Orders API

This page covers every order endpoint the POS app calls, from the **Confirm Order** button in Billing to **Order Details**, **Kitchen Master** and **Create Delivery**.

All paths are relative to `{{server}}`. Every call on this page needs:

| Header | Value |
|---|---|
| `X-Tenant` | `<your-tenant-key>` |
| `Authorization` | `Bearer <access-token>` |
| `Content-Type` | `application/json` |
| `Accept-Language` | `en` / `ar` / `ml` (also sent as `?locale=`) |

All order routes require a signed-in user. The app adds `store_id` (active store) to list and detail calls.

## How a sale reaches the server

1. Items are added to a **local cart** on the device. Billing does not call the server cart API while you scan or tap products.
2. **Confirm Order** opens Finalize Order (customer F3, delivery F4, discount F10, payment F5), then builds one `add-to-order` request.
3. With **POS_OFFLINE_SALES** on (the default, "offline-first"), the app first stores the sale on the device with its receipt identity, prints it, and then sends `add-to-order` once in the background. With it off ("online-first"), the app waits for the server: accepted = clear cart and print; rejected = keep the cart; unclear = clear without printing and flag the sale for review.
4. Sales that did not reach the server are listed in **Sales > Confirmed Orders** (Sync attention), where staff resend them with **Sync with Database**. There is no automatic retry.

## POST /api/v1/order/add-to-order

**Purpose:** creates an order from a list of items, with customer, delivery, discount and payment. It is used for confirmed sales, saved (held) orders and restaurant kitchen orders.

**Screens:** Billing (**Confirm Order** F2, **Confirm and Print** F6, **Confirm & Whatsapp**, **Save Order**), Restaurant / Attender (**Send Kitchen**, **KOT + BILL**, **Save Order**), quotation conversion, and **Sync with Database** on Confirmed Orders.

### Request fields

| Field | Meaning |
|---|---|
| `items[]` | One line per stock batch used. `product_id`, `quantity`, `price` (tax-inclusive unit price), `mrp`, `stock_id`, optional `product_variant_id`, `sale_unit_id` / `product_sale_unit_id` (pack or box), `warranty_enabled`, `offer_id` / `offer_version` when an offer applied. |
| Line snapshot (completed sale only) | `standard_unit_price` (price before offer or manual change), `item_discount_amount`, `discount_origin` (`offer` or `manual`), `offer_name(s)`, `offer_discount_type`, `offer_discount_value`, `tax_rate`, `tax_amount`, `total_price`. |
| `pricing_mode` | `completed_sale` for a printed, final sale. The server then keeps the submitted prices instead of re-pricing with today's offers. Sent only for a new executive order with a store and a full receipt identity. |
| `grand_total`, `round_off`, `tax_total`, `delivery_tax_amount` | Totals as printed. `round_off` is non-zero only with **PRICE_ROUND_OFF**. Delivery tax is always 0 from the POS. |
| `client_sale_id` | UUIDv7 made on the device. Idempotency key: resending the same sale returns the original order. |
| `receipt_number` | `store-counter-YYMMDD-sequence`, for example `2-11-261027-0003` = store 2, counter 11, 27 Oct 2026, 3rd bill of the day on that counter. |
| `issued_at`, `pos_device_id`, `counter_number` | When and where the receipt was issued. The counter number (1–999) is set in Settings > **POS Counter Identity**. |
| `customer_id`, `phone` | Customer. Without an id the server finds or creates the customer by phone. |
| `payment_method` | One method id/code, or an array for **Multi** payment. Ids from master data `PAYMENT_METHOD` (in the demo CARD = 7973, CASH = 7974) or their codes. |
| `paid_methods[]` | Split payment: `{ method, amount }` each > 0. The change is taken off the first cash (or COD) entry, so the amounts add up to the bill. |
| `paid_amount` | Single-method payments send this instead of `paid_methods`. |
| `balance` | The balance figure from the payment panel. For **Sell on Credit** it is the amount left on the customer's account. |
| `to_customer_credit` | `true` when **Excess Amount** is switched on: the overpayment is added to the customer's credit instead of returned as change. |
| `coupon_id`, `coupon_code` | Coupon applied in **Discount & Coupon**. |
| `flat_discount`, `percentage_discount`, `discount_amount` | Order discount. The discount is spread over lines in proportion, remainder on the last line. |
| `delivery_method_id`, `delivery_charge`, `delivery_date`, `delivery_time` | Delivery (F4). Date/time only when **ASK_DELIVERY_DATE** is on. |
| `address`, `address_id`, `pincode` | Delivery address for door delivery. Pincode is required when **ECOMMERCE_ENABLED** is on. |
| `car_number` | For car delivery methods. |
| `table_id`, `table` | Restaurant table. |
| `comment` | Order comment. |
| `status` | `confirmed` for Confirm; `saved` for **Save Order** (held order). |
| `quotation_id` | When converting a quotation. |
| `source_type` | Always `executive` from the POS. |
| `whatsapp_receipt` | `true` only from **Confirm & Whatsapp**. The server then sends the invoice on WhatsApp if company prop **WHATSAPP_ORDER_CONFIRMATION** is on. |

### What the server does on a confirmed sale

- Creates the order (`ORD-…`) with status `confirmed` and payment status from the payments.
- Creates the invoice automatically (in the demo `INV-OR1002060`, linked to receipt number `2-11-261027-0003`) and a receipt for the money collected (`RCP1001953`).
- Deducts stock from the batches in `stock_id`.
- If ZATCA automatic sync is set up, queues the invoice for ZATCA; otherwise its ZATCA status stays `NOT SENT`.

### Errors

| Code | Body | Meaning |
|---|---|---|
| 409 | `{ "success": false, "code": "client_sale_id_conflict", … }` | Same `client_sale_id` was already used with a different sale. |
| 409 | `{ "success": false, "code": "receipt_identity_conflict", "message": "The receipt number or client sale ID is already in use." }` | Duplicate receipt number. Usually the counter number is shared by two devices or was reset after a reinstall; fix it in **POS Counter Identity**. |
| 422 | `{ "status": "failed", "message": "Invalid payment allocation", "data": { "paid_methods": ["Payment allocations cannot exceed the order total."] } }` | Split amounts do not fit the bill (also: COD must cover the full remaining total; COD cannot create customer credit). |
| 422 | stock error body | Not enough stock (only when stock rules require it). |
| 500 | `{ "status": "failed", "message": "Validation error", "data": { … } }` | Field validation (for example an unknown payment method id). |

## POST /api/v1/order/update-order

**Purpose:** updates an existing order: add or change items of a saved order, or confirm and pay a restaurant / attender order that was sent to the kitchen earlier.

**Screens:** Edit Order (**Save Order**, **Confirm Order**, **Create Order and Print**), Restaurant **Finalize Order** on an ongoing table order.

```json
{
  "order_id": "<order-id>",
  "client_sale_id": "<uuid-v7>",
  "receipt_number": "2-11-261027-0004",
  "issued_at": "2026-10-27T16:10:00.000Z",
  "pos_device_id": "<device-uuid>",
  "counter_number": 11,
  "phone": "0551234567",
  "transaction_number": "",
  "payment_method": "CASH",
  "paid_amount": "438.0",
  "source_type": "executive",
  "balance": "0.0",
  "coupon_id": null,
  "status": "confirmed",
  "table_id": "<table-id>",
  "delivery_charge": 0

```

`order_id` is required and must exist. Items and customer are not sent: the order already has them. A completed sale cannot be changed (`409` `completed_sale_immutable`).

## POST /api/v1/order/confirm-order

**Purpose:** confirms an order that is still `init` or `new` (a saved order). Body: `{ "order_id": "<order-id>", … payment fields … }`. Returns `409` `completed_sale_immutable` for a completed sale, `403` `tenant_mismatch` if the order belongs to another company.

| `payments` | Payment breakdown by method. For Layla's order: `{ "CARD": 400, "CASH": 258 }`. |
| `customer_details`, `kyc_info` | **Customer Information** (B2B shows VAT and CR numbers). |
| `order_props[]` | `ORDER_STATUS` history, `ORDER_TOKEN_NUMBER`, and when present `CUSTOMER_PHONE`, `CUSTOMER_EMAIL`, `CUSTOMER_ADDRESS`, `DELIVERY_ADDRESS`, `DELIVERY_PHONE`, `DELIVERY_DATE`, `DELIVERY_TIME`, `CAR_NUMBER`, `BALANCE`. |
| `return_state`, `order_returns` | Returned quantities; drive the **Return** button. |
| `packing`, `external_delivery_job` | **Packing** and **Shipping Details**. |
| `invoice_hash` | Used for the public invoice link. |
| `kot_cancel_queue` | KOT cancellation events waiting to be printed. |

## Order status, payment status and cancel

### Allowed status changes

| From | Can move to |
|---|---|
| init | new, confirmed, cancelled |
| new | confirmed, cancelled |
| confirmed | processing, shipped, cancelled |
| processing | shipped, delivered, cancelled |
| shipped | delivered |
| delivered | (final) |
| cancelled | (final) |

Shipped or delivered orders cannot be cancelled: use a sales return. An order with a processed sales return cannot be cancelled. Shipping needs packing to be complete.

### POST /api/v1/order/order-change-status

**Screen:** **Order Status** action on the list and on Order Details.

```json
{
  "order_id": "<order-id>",
  "status": "processing",
  "refund_amount": 0,
  "payment_method": 7974,
  "delivery_charge_refundable": false,
  "delivery_logistics": "Door Delivery"
}
```

| Field | Rule |
|---|---|
| `order_id` | Required. |
| `status` | Required: `init`, `new`, `confirmed`, `processing`, `shipped`, `delivered`, `cancelled` (subject to the table above). |
| `refund_amount`, `payment_method`, `delivery_charge_refundable` | When moving to `cancelled` with a refund. `payment_method` is a `PAYMENT_METHOD` id. |
| `delivery_logistics` | Optional carrier text. |
| `reason` | Optional, up to 500 characters. |
| `cod_collected_amount` | Optional, when a COD order is delivered. |

### POST /api/v1/order/order-change-payment-status

**Screen:** **Payment Status** action.

```json
{ "order_id": "<order-id>", "status": "paid", "amount": 658, "payment_method": 7974 }
```

| Field | Rule |
|---|---|
| `status` | Required: `pending`, `paid` or `failed`. |
| `amount` | Required unless `paid_methods` is sent. |
| `payment_method` | Optional `PAYMENT_METHOD` id. |
| `paid_methods[]` | Optional split: `{ method, amount }`. |

### POST /api/v1/order/cancel-order

**Screen:** **Cancel Order** row action.

```json
{ "order_id": "<order-id>", "refund_method": 7974, "refund_amount": 658, "delivery_charge_refundable": false }
```

Optional `reason`. Success: `{ "status": "success", "message": "Order cancelled successfully", "data": { …order… } }`. A transition that is not allowed returns `422` with the reason.

## Kitchen (KOT) item statuses

Kitchen item statuses come from master data `CART_ITEM_STATUS` and their **ids differ per company**, so always read them first.

### GET /api/v1/cart/cart-item-statuses

Captured response (trimmed):

```json
{
  "status": "success",
  "message": "Available cart item statuses",
  "data": [
    { "id": 2019, "value": "READY", "description": "Ready", "translations": [] },
    { "id": 2020, "value": "SERVED", "description": "Served", "translations": [] }
  ]
}
```

The third status is `START` (started / preparing). An item with no status is **NEW** (pending). Kitchen Master tabs map to them: Pending = no status, Preparing = START, Ready = READY, Served = SERVED.

### POST /api/v1/cart/update-cart-item-status

**Screen:** **Mark Ready** per item in Kitchen Master > Order Details, and **Mark As Served**.

```json
{ "cart_item_id": "<cart-item-id>", "status_id": 2019 }
```

Both fields are required. Returns "Cart item status updated successfully", or an error if the status id is not an active `CART_ITEM_STATUS` value.

### POST /api/v1/order/update-order-items-status

**Purpose:** sets the status of many items at once (Start Cooking, mark the whole order served).

```json
{ "order_id": "<order-id>", "status_id": 2020, "all": true }
```

| Field | Rule |
|---|---|
| `order_id` | Required. |
| `status_id` | Optional `CART_ITEM_STATUS` id. Without it the items go to `START`. |
| `all` | `true` = every item. Otherwise only items that have no status yet. |

Response:

```json
{
  "status": "success",
  "message": "Order items status updated successfully",
  "data": { "order_id": "<order-id>", "order_number": "ORD-004852", "items_updated": 2, "status": "SERVED", "updated_at": "…" }
}
```

### POST /api/v1/order/acknowledge-kot-print

**Purpose:** after the KOT (or a KOT cancellation) is printed, removes those events from the order's KOT queue so they are not printed twice.

```json
{ "order_id": "<order-id>", "event_ids": ["<event-id>"] }
```

Returns "Events acknowledged successfully", or "Nothing to acknowledge" when the queue is empty.

## Server cart (legacy)

Billing keeps the cart on the device. These cart endpoints are still used by the older cart and edit screens.

### POST /api/v1/cart/add-to-cart

```json
{ "customer_id": "2767", "quantity": 1, "product_id": "<product-id>", "source_type": "executive", "cart_id": "<cart-id>", "price": "210", "comment": "" }
```

`cart_id`, `price` and `comment` are optional. Optional `product_variant_id` for variants.

### POST /api/v1/cart/remove-from-cart

```json
{ "cart_item_id": "<cart-item-id>", "cart_id": "<cart-id>", "action": "update_quantity", "quantity": 2, "customer_id": "2767" }
```

`action` is `remove_item`, `clear_cart` or `update_quantity`. `cart_item_id` is required for `remove_item` and `update_quantity`; `quantity` for `update_quantity`.

### GET /api/v1/cart/executive/list-cart-items

Params `customer_id` (required), `cart_id`, `store_id`. Returns the cart: `id, customer_id, item_count, store_id, cart_items[{id, product_id, product_name, quantity, product_unit, unit_price, mrp, total_price, tax_rate, tax_amount}], price_summary{sub_total, total_tax, net_total, discount, net_payable}`. Errors: "Customer ID is required", "Cart not found/No incomplete cart".

### POST /api/v1/cart/change-cart-item-price

```json
{ "cart_item_id": "<cart-item-id>", "unit_price": 200 }
```

Optional `tax_id[]`. Returns "Cart item price updated successfully!" with the line.

## Packing, documents and external delivery

These actions are on **Order Details** for roles `sales_executive` and `restaurant_sales`. Saving packing requires the sales-executive shipping permission (otherwise `403` "Sales Executive permission required.").

### GET `/api/v1/order/packing/{order_number}`

Returns the packing record: status, packed at, packed by, photo and video URLs.

### POST `/api/v1/order/packing/{order_number}`

`multipart/form-data`:

| Field | Meaning |
|---|---|
| `packed_by_user_id` | Staff id from `packing-staff`. |
| `packed_by_name` | Free-text name. |
| `packed_at` | Date-time. |
| `packing_photos[]` | Image files, up to 20 MB each. |
| `photos_to_delete[0]`, `[1]`… | Paths of photos to remove. |

Only `confirmed`, `processing` or `shipped` orders can be packed (`422` otherwise). Video is not accepted here.

### GET /api/v1/order/packing-staff

Users who can be chosen as **Packed by**.

### GET `/api/v1/order/documents/delivery-note/{order_number}`
### GET `/api/v1/order/documents/delivery-invoice/{order_number}`

Return the PDF bytes of the Delivery Note ("Goods Delivery Receipt") and Delivery Invoice. They need the auth headers, so the app downloads them and opens the file; they cannot be opened as plain links.

### GET /api/v1/order/external-logistics

Active external carriers for **Create Delivery**.

### GET `/api/v1/order/external-logistics/{external_logistic_id}/warehouses`

Pickup warehouses of one carrier.

### POST `/api/v1/order/order-details/{order_number}/external-delivery`

Example body (illustrative values):

```json
{
  "external_logistic_id": 3,
  "warehouse_id": 5,
  "shipping_service": "express",
  "transport_mode": "surface",
  "weight": 2.5,
  "package_count": 1,
  "length": 30,
  "breadth": 20,
  "height": 15,
  "shipping_charge": 0,
  "dispatch_date": "2026-10-28",
  "expected_delivery_at": "2026-10-30",
  "payment_mode": "Prepaid",
  "tracking_url": "https://carrier.example/track/123",
  "external_shipment_id": "SHP-123",
  "remarks": ""
}
```

| Field | Values |
|---|---|
| `shipping_service` | Master data `SHIPPING_METHOD`: parcel, speed_post, registered_parcel, express. |
