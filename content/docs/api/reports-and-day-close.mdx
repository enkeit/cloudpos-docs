# Reports and Day Close API

This page covers the endpoints behind the **Reports** menu and **Sales > Day Sale Closing** (Open Shift, Day Close, Daily Sales Closes list and detail). All calls need `X-Tenant` and `Authorization: Bearer <access-token>` (see [API overview](/docs/api)). All report routes require a signed-in user.

Dates are sent as `YYYY-MM-DD` unless stated otherwise. The company time zone (demo: Asia/Riyadh) decides what "today" means.

## Report endpoints at a glance

| Report (menu label) | Endpoint | Permission to see the menu item |
|---|---|---|
| Sales Executive Reports (My Sales) | `GET sales-executive-report` | `menu.reports.sales_executive.access` |
| Executive Reports (admin) | `GET sales-executive-report-admin` | `company_admin`, or `menu.reports.executive_summary.access` for roles other than sales_executive |
| Sales Report | `GET sales-report` | `menu.reports.sales_report.access` |
| Discount Sale Report | `GET discount-sales-report` | `menu.reports.discount_sales.access` |
| Product Sales Report | `GET product-sales-report` | `menu.reports.product_sales.access` (or legacy `page_ProductSalesReport`) |
| Customer Transaction Reports | `GET transaction/customer-transactions` | `menu.reports.customer_transactions.access` |
| Supplier Transaction Reports | `GET suppliers/list-transactions` | `menu.reports.supplier_transactions.access` |
| Stock Report | `GET stock-report` | `menu.reports.stock.access` or `company_admin` |
| Non-Stock Report | `GET non-stock-report` | `menu.reports.non_stock.access` |
| Consumed Stocks Report | `GET consumed-stocks-report` | `menu.reports.consumed_stock.access` |

## GET /api/v1/sales-executive-report

**Purpose:** totals for the signed-in executive: orders, total, online (card/UPI), cash and credit sales, and money collected.

**Used by:** **Reports > Sales Executive Reports** (My Sales Report). With no dates it shows today.

**Query parameters**

| Name | Type | Required | Description |
|---|---|---|---|
| `dateFilter` | string | yes | `today` (default when no dates are picked) or `custom` |
| `dateFrom` | date-time | with `custom` | Start, for example `2026-10-01 00:00:00` |
| `dateTo` | date-time | with `custom` | End, for example `2026-10-27 23:59:59` |
| `store_id` | integer | no | Active store (always sent by the app) |

**Response (200)** (one row per executive; phone masked)

```json
{
  "status": "success",
  "message": "data found",
  "data": [
    {
      "name": "salesexecutiv2",
      "phone": "<phone>",
      "order_count": 1301,
      "total_sales": 321739.5,
      "upi_sales": 1127,
      "card_sales": 237735.5,
      "upi_on_sale": 1127,
      "card_on_sale": 232919.5,
      "other_on_sale": 2214,
      "online_sales": 236260.5,
      "cash_sales": 48816.8,
      "credit_sales": 36662.2,
      "collected_sales": 9215,
      "total_payment": 294292.3,
      "total_payment_received": 294292.3,
      "total_collected_on_sale": 285077.3,
      "payment_breakdown": { "UPI": 1127, "CARD": 232919.5, "Other": 2214 }
    }
  ]
}
```

Field meaning: `*_on_sale` is money taken at the moment of sale; `collected_sales` is credit collected later; `credit_sales` is the amount sold on credit; `total_payment_received` is all money received in the period.

**Purpose:** order-level sales list with totals, the same report as the web admin.

**Used by:** **Reports > Sales Report**. Date range defaults to **This Month**. For a `sales_executive` the Stores and Sales Executive filters are locked to the user's own store and name.

**Query parameters**

| Name | Type | Required | Description |
|---|---|---|---|
| `period` | string | no | `this_month` (default), `last_month`, `last_3_months`, `custom` |
| `from` | date | with `custom` | Start date |
| `to` | date | with `custom` | End date |
| `store_ids` | comma list | no | Stores filter. When empty the report covers every store the user may see (the active store is not added automatically) |
| `sales_executive_ids` | comma list | no | Sales executives filter |
| `payment_method_ids` | comma list | no | Payment methods filter |
| `delivery_method_ids` | comma list | no | Delivery modes filter |
| `category_ids` | comma list | no | Categories filter |
| `product_ids` | comma list | no | Products filter |
| `customer_ids` | comma list | no | Customers filter |
| `sort_direction` | string | no | `asc` or `desc` |
| `page`, `per_page` | integer | no | Paging |

**Response (200)** (illustrative row; field names the app reads)

```json
{
  "status": "success",
  "data": {
    "data": [
      {
        "order_id": 7037,
        "order_number": "ORD-004851",
        "order_date": "2026-10-27T11:40:00Z",
        "order_value": 658.0,

        "sales_executive_id": 516,
```

`summary` holds totals over **all** matching rows, not just the page. The app also accepts `id`, `created_at`, `total_price`/`grand_total`, `payment_method`, `delivery_mode`, `sales_executive` and `store` as alternative names. The executive picker list comes from `GET list-sales-executives`.

## Daily sales close (shift and day close)

Day close endpoints use the `{ "success": true/false, "message", "data" }` envelope and return validation errors as **422** with an `errors` map.

### Business rules

- A day close record has status `draft` (shift opened, not closed) or `closed`.
- **Only one open draft per user per store.** Opening another returns **409**.
- A close covers the user's transactions **after the previous close's `closing_transaction_id`**, limited to the **last 7 days**. Older unclosed transactions are skipped and a `notice` explains this.
- Cash counts use the `CASH_DENOMINATIONS` master data (default notes 500, 200, 100, 50, 20, 10, 5, 1). A breakdown row with a denomination outside that list is rejected.
- Short or excess cash is calculated against the expected closing cash.
- When no shift name is given the server uses the default "Swift".
- Before closing, the app warns **Sync orders before Day Close?** when local sales are still waiting in **Sales > Confirmed Orders**. You can cancel, review them, or **Close anyway** (unsynced sales are then missing from this close).
- Website setting **COMPULSORY_SHIFT_OPEN** blocks billing until a shift is opened. **COMPULSORY_DAY_CLOSE_REGISTER** makes the app offer a pending day close (Yes / No) right after store selection.

### POST /api/v1/daily-sales-close/open

**Purpose:** open a shift (creates a `draft` day close with opening cash).

**Used by:** **Open Shift** dialog (store, shift name, business date, opening time, opening cash balance with denomination breakdown, notes, **Save Opening Draft**).

**Request body**

```json
{
  "store_id": 2,
  "shift_name": "Morning",
  "business_date": "2026-10-27",
  "opening_date": "2026-10-27",
  "opening_time": "09:00:00",
  "opening_cash_in_hand": 500,
  "opening_cash_breakdown": [
    { "denomination": "100", "count": 4 },
    { "denomination": "50", "count": 2 }
  ],
  "notes": ""
}
```

| Field | Rule |
|---|---|
| `store_id` | required, must be a store of this company |
| `shift_name` | optional, max 255; default "Swift" |
| `business_date`, `opening_date` | optional dates; default today in the company time zone |
| `opening_time` | optional `HH:MM:SS`; default the store's shift opening time |
| `opening_cash_in_hand` | optional number, 0 or more |
| `opening_cash_breakdown` | optional array of `{denomination, count}` |
| `user_id` | optional; default the signed-in user |

**Response (201)**

```json
{
  "success": true,
  "message": "Day close draft opened successfully",
  "data": { "id": 510, "status": "draft", "shift_name": "Morning", "business_date": "2026-10-27", "...": "same fields as list rows" }
}
```

**Errors:** 422 validation (`errors.opening_cash_breakdown` for a bad denomination), 409 `"A draft day close is already open for this store."` with the existing draft in `data`.

### GET /api/v1/daily-sales-close/pending-status

**Purpose:** tell the app whether the user must close an older day before selling.

**Used by:** store selection (when **COMPULSORY_DAY_CLOSE_REGISTER** is on) and the Day Sale Closing screen.

**Query parameters**

| Name | Type | Required | Description |
|---|---|---|---|
| `store_id` | integer | yes | Active store |
| `user_id` | integer | no | The app sends the signed-in user; the server uses the token's user |

**Response when nothing is pending**

```json
{
  "success": true,
  "data": {
    "pending_day_close": false,
    "can_open_shift": true,
    "open_draft": null,
    "business_date": "2026-10-27",
    "opening_transaction_id": 20040,
    "message": null
  }
}
```

`pending_day_close` is `true` and `can_open_shift` is `false` while a draft (open shift) exists; `open_draft` then holds that draft.

**Response when an older day is unclosed**

```json
{
  "success": true,
  "data": {
    "pending_day_close": true,
    "can_open_shift": false,
    "requires_confirmation": true,
    "business_date": "2026-10-26",
    "message": "You did not close your last day sales for 26-Oct-2026.",
    "confirmation_message": "Do you want to close it now?",
    "opening_transaction_id": 19980,
    "closing_transaction_id": 20039,
    "opening_date": "2026-10-26",
    "opening_time": "09:00:00",
    "closing_date": "2026-10-26",
    "closing_time": "21:47:09"
  }
}
```

A `notice` key is added when older transactions beyond the 7-day window were skipped.
